# Operations

Notes for running and operating the platform. Phase 1 covers local and
single-VM deployment; later phases add scheduling, monitoring and backups.

## Services (docker-compose.yml)

| Service | Purpose | Port |
| --- | --- | --- |
| `postgres` | PostgreSQL 16 + pgvector; provisions the least-privilege `news_app` role | 5432 |
| `redis` | Queue broker / cache (used from Phase 7) | 6379 |
| `migrate` | Runs `alembic upgrade head` then `python -m app.cli seed`, then exits | — |
| `backend` | FastAPI API (uvicorn) | 8000 |
| `worker` | Background workers (placeholder until Phase 7) | — |
| `frontend` | Next.js UI | 12000 |

## Bring up / tear down

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f backend
docker compose down            # keep data
docker compose down -v         # DESTROY database + redis volumes
```

## Environment

Copy `.env.example` to `.env` and set real secrets. Key variables:

- `ADMIN_API_TOKEN` — required in production; guards admin endpoints.
- `DATABASE_URL` — the app connects as `news_app`, never the superuser.
- `APP_DB_PASSWORD` — password for the provisioned app role.
- `TRUST_PROXY_HEADERS` — set `true` only behind a proxy you control, so
  `X-Forwarded-For` is trusted for country resolution.
- `AI_*` / `IMAGE_*` — unused in Phase 1; wired from Phase 4/6.

## Database provisioning and least privilege

`CREATE EXTENSION` requires superuser, so `vector` and `pg_trgm` are created by
`infrastructure/docker/postgres-init/01-app-role.sh` at first boot, alongside
the `news_app` role. Migration `0001` only verifies the extensions exist. The
application never needs superuser rights.

## Migrations

```bash
cd backend
alembic upgrade head                       # apply
alembic revision --autogenerate -m "..."   # create after model changes
alembic downgrade -1                       # step back
```

Autogenerated migrations import `pgvector.sqlalchemy` when a vector column is
present; keep that import.

## Seeding configuration

```bash
cd backend
python -m app.cli seed            # config/*.yaml → database (idempotent)
python -m app.cli export-seeds    # config/*.yaml → database/seeds/*.json
```

Seeding is idempotent: re-running updates existing rows by slug.

## Health checks

```bash
curl localhost:8000/health
# {"status":"ok","env":"development","database":"ok","source_count":47}
```

The backend container has a `HEALTHCHECK` hitting `/health`, so orchestrators
can restart it automatically.

## Admin endpoints

Admin/ops endpoints require the shared token:

```bash
curl -H "X-Admin-Token: $ADMIN_API_TOKEN" localhost:8000/sources/bbc-world/health
```

Requests without a valid token get `401`.

## Failure handling expectations (Phase 2+)

- A failing source is recorded (`source_health`) and retried with backoff; it
  must not affect other sources.
- AI API failures queue and retry; image failures publish the article without
  an image.
- Every job carries an idempotency key so retries never duplicate output.

## What to monitor (Phase 7 target)

Sources online/offline, reports ingested/hour, duplicates detected, events
created/merged, articles generated/rejected, fact-check failures, AI failures,
queue size, processing latency, database size, API cost. Plus an accuracy
dashboard: published articles, fact-validation failures, corrections, source
conflicts, low-confidence publications, duplicate publications.
